### J1. Approve the sleeping-node write test (Stage 0 Z4)

| | |

| Issue | [#5](https://github.com/jayanty/ha-device-links/issues/5) |
| Blocks | The `pending_wakeup` path is unproven against hardware |
| Needs | Approval to write to node 40 (Master Bedroom Remote, ZEN37 800LR), plus a button press to wake it |

Stage 0 confirmed the mechanism exists: every association write method takes

cannot pass.

Instructed on 2026-09-05 to complete as much as possible without waiting, using reasonable
defaults, and to defer deployment until the open items are addressed. Every assumption made

discovered later in the code.

**Deployment to Jayant's Home Assistant is paused.** The last deployed commit is the Phase 1C
merge. Nothing since then has been sent, and nothing will be until the items in section 1 are
addressed. The deploy loop itself is proven and unchanged; it is simply not being used.

What that costs is worth naming, because T50 was the bill. A paused deployment means no
screen of this product has been opened by a person since Phase 1C, so anything that is only
true when the panel meets the backend is true only if a test says so. `rules/upsert` refused
every rule the panel could save from Phase 1E until T50 was closed, and every layer's tests
passed throughout. `tests/test_panel_save_path.py` is the standing answer: it builds what
the editor builds, from the payloads the panel is handed, and pushes it through the real
handlers. Anything else the panel will only do for the first time on a real instance should
get the same treatment rather than waiting for a deploy that is not coming yet.

The field stays empty and stays out of identity; `backends/zwave.py`'s comment is the only thing left that is out of date. |
| T15 | A cancel that arrives during a retry backoff is acted on only after the wait | The runner waits out the 1 s or 2 s and then stops, so a cancel can take up to two seconds to take effect. The panel's switch instead stores the change with `rules/upsert` and opens the plan dialog, and puts the switch back if the plan is cancelled. That keeps the "no write without a confirmed plan" rule whole, and it means a burst of toggles from the panel is limited by a human confirming each plan rather than by `RuleToggleLimiter`. The switch entity and the service still go through the limiter, which is where an automation would come from. |
| T40 | The panel's own English strings are still not translatable, and there are now many more of them | T30 named the problem when the panel was a shell with five tab labels. Tasks 5 to 8 added several hundred words of UI copy, so the cost of closing T30 has gone up and the reason has not changed. Everything the backend says is still localised; everything the panel says is still English literals. |
| T41 | Nothing removes a managed Zigbee group whose rule was deleted while Home Assistant was down | The `Backend` protocol writes one link at a time and never sees a rule, so the adapter cannot know that a rule has stopped existing. In the normal case nothing is owed: disabling a rule plans removals, the last member comes out of the group, and the group goes with it. What is left is the same gap T11 describes, seen through a group: a rule deleted (or edited to point elsewhere) stops claiming its links, they become unmanaged, and the `dl_` group they sit in is reported rather than removed. `ZigbeeBackend.async_drop_managed_group` and `managed_group_rule_ids` are the two halves of the answer, both tested, and nothing calls them: wiring them up means giving the coordinator a way to tell a backend that a rule is gone, which is a deliberate change to the protocol rather than a quiet special case in core. A narrower case sits under the same heading: a managed group deleted by hand while bindings still point at its id. Zigbee2MQTT drops those bindings itself when it deletes a group, so it should not arise; if it did, the next apply recreates the group under a new id and the dead binding is reported as an unmanaged link to `group:<id>` rather than being removed. |
| T43 | A Zigbee binding table's real size is not reported, so capacity is a bound rather than a measurement | `zigbee_protocol.BINDING_TABLE_CAPACITY` is 8 per endpoint cluster. Zigbee2MQTT does not publish a device's binding table size and the Zigbee specification leaves it to the manufacturer, so there is no number to read. Too low blocks a plan that would have worked; too high lets one through that the device refuses, which is now reported per cluster rather than silently. Decision D5's managed group is what keeps this from mattering: a group is one entry however many members it has. |
| T44 | The planner counts group capacity per device and group, not per endpoint | `planner._planned_adds` keys its capacity count on `(source identity, emitter_group)`, and `_capacity_of` takes the first emitter whose `group_ids` hold the group. On Zigbee the writable slot is `(endpoint, cluster)`, so two endpoints driving `genOnOff` share one bucket and the reporting bindings on a switch's load endpoint count against its paddle's. Latent rather than active on this network: the counts are small and every Zigbee emitter reports the same capacity, so nothing is blocked today. The same conflation in `executor.JobRunner._is_system` was narrowed in Phase 2A and closed for good with T49, which is where the reasoning about what a slot is per protocol now lives (`backends.base.SystemScope`). This one is left alone because no test fails on it and changing the planner changes every plan token. |
| T45 | Zigbee device settings are read as "not reported" and refused on write | The four Inovelli adapters (`smart_bulb_mode`, `local_protection`, `remote_protection`, `binding_off_to_on_sync_level`) ship in the profile entries, and their property names and payload labels come from Zigbee2MQTT's converter rather than from the G1 capture, which trimmed `definition.exposes` out. A write would also need the `set` and state round trip, which nobody has observed either, so building one would stack a second unverified model on the first and prove only that the two agree. Nothing can reach it today in any case: the compiler emits a setting write only for `mirror_hub_commands`, a Z-Wave concept, and the executor cannot carry out a `set_param` item at all (T16). Closing it means subscribing to each device's own state topic and confirming the property names, which G2 or a fresh capture would settle. |
| T46 | A `genLevelCtrl` binding a rule only half asked for is reported as unmanaged | One cluster carries setting a level and holding to dim, so a rule that asks for one of them gets both, and the one it did not ask for reads back as a link nobody claims. Reported rather than removed, which is safe, and worded as though somebody else made it, which is not quite true: Device Links made it, as an unavoidable side effect of what the user did ask for. Closing it means a third ownership state between "ours" and "somebody's own", which is a change to what the panel shows and to what `managed_by` means. Cheap alternative: have the rule editor offer the two level features as one choice on a Zigbee rule, which is what the hardware offers. |
| T47 | A binding on a cluster Device Links cannot drive is reported as a status report | `zigbee_protocol.features_of_binding` answers `STATUS_REPORT` for `seMetering`, `manuSpecificInovelli` and the rest, the same answer the Z-Wave side gives a group that issues nothing usable. It keeps a device's binding table described whole, which is what the capacity count and the device view need, and it is a slight overstatement: those entries do not all report anything. Nothing acts on it (no emitter maps a feature to those clusters, so none can ever be desired), so this is wording rather than behaviour. |
| T51 | A Zigbee2MQTT bridge that starts after Device Links is not adapted until a reload | `_async_build_zigbee` subscribes once at setup and waits ten seconds for the retained `bridge/devices`. A broker that is up with Zigbee2MQTT still starting, or a base topic that was wrong and has been corrected in the add-on rather than in our options, leaves the entry loaded with no Zigbee backend until somebody reloads it. It is a warning in the log naming the topic, and the Z-Wave half of the house keeps working. Refusing to set up instead (`ConfigEntryNotReady`) was rejected: somebody who runs an MQTT broker for something else entirely and no Zigbee2MQTT would then have Device Links retrying for ever over a bridge they do not own. Closing it properly means watching for the retained payload arriving later and building the backend then, which is a second setup path. |
| T52 | Only one Zigbee2MQTT instance is adapted | The exact shape of T22 one protocol along. The options flow takes one base topic, `BackendId` is one key per protocol, and `DeviceHandle.protocol_id` is the IEEE address with no instance in it, so two instances on one broker cannot both be represented without keying the backend map and the handle on the instance as well. A user with two configures the one they want Device Links to manage and sees nothing at all of the other: no devices, no links, no error. That is the same answer a second Z-Wave network gets, and it is the reason the base topic is a setting rather than a constant: the room to grow is there, and only the wiring is missing. |
| T53 | `DeviceCapabilities.receiving_endpoint` takes the lowest endpoint that can receive | Added for T48, and derived rather than curated: the Zigbee adapter answers with the lowest endpoint whose input clusters carry a bindable feature, which is endpoint 1, the load, on every switch in the G1 capture. On a device with two receiving endpoints (a two-gang switch) that is a choice made for the user. It is the same approximation `DeviceCapabilities.receivable` already makes by being a union across endpoints, and it is only consulted where the user was offered no choice at all, so nothing silently overrides something they asked for. **Closing T50 widened where that is**: it used to be one line of the compiler (the reverse leg of a two-way rule) and it is now the target endpoint of every rule saved from the panel, because the editor has no endpoint picker yet (T56). The number is right on every device in the G1 capture and the panel shows it beside each target while it is being ticked, so a wrong one is visible rather than silent. A curated entry naming the receiving endpoint per model is the obvious close, and it wants a device that needs it first. |
| T54 | `Emitter.is_lifeline` is always False and nothing can make it true | `zwave_protocol._usable_groups` drops lifeline groups before an emitter is built, and the Zigbee side sets it False outright, so no emitter in the product has ever carried True. It is serialized to the panel and read by `services._group_view`, both of which therefore ask a question with one possible answer. Harmless, and misleading to the next person who reaches for it as the answer to "is this slot the protocol's own" (which is what T49 needed and what `backends.base.SystemScope` now answers). Either give it a meaning or take it out; taking it out is a change to the panel's `Emitter` interface and so to the bundle. |
| T56 | A target's endpoint is a default the user is shown, not a choice they make | PRD Section 7.2 asks for an endpoint picker when a target is multi-channel, and closing T50 stopped short of one: the targets step fills each target's endpoint from `DeviceCapabilities.receiving_endpoint` and shows it as a chip beside the device, so the default is visible and editable only by not choosing that device. That is right for everything on this network (every Z-Wave device is single-endpoint and answers None, and every Zigbee switch in the G1 capture has one bindable endpoint, the load) and wrong for a two-gang switch, where the default takes the lower gang and the user has no way to ask for the other. It was not built now because a picker needs the list of endpoints a device can receive on, and nothing carries one: `DeviceCapabilities` has `receiving_endpoint` and `receivable`, both already flattened across endpoints (T53), so building the picker means widening the capability model in both adapters and the fixtures behind them. Until then the visible chip is the mitigation: the number a rule will use is on screen before it is saved, and again in the review step's link list, rather than only in the payload. One thing to carry into the picker when it is built: `_toggleTarget` refills a target's endpoint from the default on every tick, so a rule that named a non-default endpoint (from an imported file, or from the picker itself) would lose it if the user unticked and re-ticked that device. Harmless while nothing can name one. |
| T58 | Choosing a source device twice quickly can leave the editor showing the first device's controls | `rule-editor._chooseSource` starts `devices/get` and does not carry a token, so clicking device A and then device B while A's read is in flight resolves A last and leaves `_sourceDetail` describing A while the draft names B. The user then picks a control that belongs to a device the rule is not about. Pre-existing, and worse since T50: the draft now takes the source endpoint from that same emitter, so a second wrong field rides the same race. What limits it today is that the compiler resolves the emitter against the device the rule names and answers `unknown_emitter` when that device offers no such control, so the review step usually refuses rather than saving something wrong. Usually, not always: two devices of the same model offer the same emitter ids, and every Z-Wave emitter answers endpoint 0, so a mix-up between two identical switches would compile. The read is also a cached one that returns in milliseconds, which is why nobody has seen this. Closing it is a request token compared on arrival, in one method. |
| T60 | A swap cannot cross protocols | `swap._refusals` refuses a replacement on a different backend outright. A Z-Wave switch really can be replaced by a Zigbee one, and somebody who does that today deletes and re-writes every rule by hand. Rewriting the handle is the easy half; what makes it a new rule rather than a rewritten one is that every target's addressability changes (a Z-Wave association names a node, a Zigbee binding names an endpoint and a cluster) and the target set may not survive at all. The refusal says so in the message rather than producing a profile whose every rule silently compiles to nothing. |
| T61 | `swap/apply` re-points a rule's links by selecting them as unmanaged | The removals on the old device are carried into the apply as `remove_unmanaged` fingerprints, which is a real per-link opt-in and exactly the links the preview showed, and it is a workaround for T11: ownership is derived from what the active profile compiles to, so the moment the rules point at the replacement the old device's entries stop being claimed by anything. With a per-link ownership record written at apply time (T11's proper close), the swap would carry ownership across instead and the selection would be unnecessary. Nothing is unsafe about it today: the fingerprints are computed from what the rules themselves claimed before the rewrite, never from what happens to be on a device. |
| T62 | A device that has left the network is noticed at setup and at an unscoped Verify, and not in between | Added for FR-S3, which cannot fire for a device that disappears while Home Assistant is running unless the cache lets go of it. `coordinator._forget_unlisted` drops the handle, capabilities and observed state of a device a backend answered a **listing** without, so it reads as absent rather than as unavailable; `coordinator.async_relist` is the only path that asks, and `async_setup` and an unscoped `verify` are the only two callers. Deliberately not on a timer: it re-reads every device on the network, and a schedule would be radio traffic for a question whose answer changes when a person changes it. Three limits worth knowing. An empty listing never prunes, because Zigbee2MQTT republishes `bridge/devices` while it restarts and a momentarily empty list would take every Zigbee device off at once. A *partial* listing would prune, which neither adapter is known to produce (the Zigbee one raises when the bridge is offline, so the coordinator keeps the cache instead, and the Z-Wave one reads the driver's node map) and which would in any case correct itself at the next listing. And a device that leaves while nobody presses Verify is unavailable rather than absent until then, which is E4's answer and not a wrong one. |
| T63 | A swap's plan is rebuilt after the token is checked, and the two are compared rather than being one object | `swap/apply` verifies the token against a plan built exactly the way the preview built it, then stores the rewritten rules and plans again, because storing is what moves ownership onto the replacement (T11 and T61). `_refuse_a_different_plan` compares the two item for item and refuses with `plan_out_of_date` if they differ, so the write is the work that was shown even though the object is not the one the token belongs to. They are equal by construction today, and the comparison is there because that is a property of code somebody will change. Closing it properly means the token covering the rules as well as the observed state, which changes what every plan token means. |
| T64 | A rollback is one command with two modes, told apart by whether a plan token was sent | `snapshots/rollback` with no `plan_token` answers with the plan and writes nothing; with one, the token has to match and the work is applied. PRD Section 8.7 lists one command, and the safe direction is the default (a caller that forgot the token gets a preview, never a write), which is why it is shaped this way rather than as two. It is still implicit: a reader of the API has to know that the absence of a field is what makes it read-only. A separate `snapshots/preview` would say so in its name, and would be a sixth command the PRD does not list. |
| T65 | Rolling back a device removes what an enabled rule still wants, and the rule then reads as drifted until it is applied again | Deliberate and named in the preview (`returns_on_next_apply`), and it is the honest consequence of a rollback restoring devices while leaving the profile alone. What is missing is the shortcut: a user who wants those links gone for good has to go to the Rules tab and disable each rule by hand, and the notice in the dialog tells them to. Offering "disable these rules as well" from inside the rollback dialog would close it, and it is a second write with its own consequences (a disabled rule's links are planned for removal everywhere, not only on the snapshot's devices), so it wants its own confirmation rather than a tick box on somebody else's. |
| T66 | The mirror never reads a file back, so a hand-edited one is silently overwritten | One direction on purpose: a rule about somebody's lights should not change because a text editor and a restart agreed on something, and `profiles/import` is the deliberate way in. What that costs is a user who edits a mirrored file and finds their change gone at the next profile change, with nothing having said so. The header names the file as generated, and the option's own description says it is a copy, which is the mitigation. Closing it properly means either watching the directory and offering an import (a plan, a confirmation, and a file-watcher this integration does not have) or writing the files read-only, which is a lie about what the user may do with their own configuration directory. |
| T67 | The mirror writes on the coordinator's own listener, which fires for device reads as well as profile changes | Every coordinator update calls the mirror, which compares the text it would write against the text it last wrote and arms nothing when they agree. That is correct and it is also `dump_profile` over every profile on every device read, which is a few milliseconds on this network and grows with the number of rules rather than with the number of devices. A cheaper trigger would be the coordinator saying which kind of change it just made, which is a new distinction in `async_update_state` that nothing else needs yet. |
| T68 | The mirror can be pointed at a directory that already holds other files, and only says so in the option's description | `_is_ours` means nothing there is deleted that this integration did not write, so the damage a misdirected mirror can do is bounded at leaving `.yaml` files somebody did not ask for. What it does not do is warn: a path that is not empty when the mirror is first switched on is exactly the case worth a word, and it is also the case (a user pointing it at an existing `packages/` directory on purpose) where a warning every start would be noise. Wants deciding rather than building. |
| T69 | A Z-Wave rule's entities need the Z-Wave backend to have been built, and it is built once at setup | Since T57 the registry identifier comes from the adapter, so `rule_entity._upstream_identifier` answers None when `_build_zwave` found no loaded `zwave_js` entry with a driver. On a start where `mqtt` comes up and `zwave_js` has not yet, setup succeeds with one backend and every Z-Wave rule is unattachable for the life of that entry: no switch, no status sensor, and no Z-Wave device openable in the panel until the entry is reloaded. Before T57 the identifier came from the handle alone and the device registry answered whatever the backend was doing. Nothing is lost (the entity registry entries are not removed, because the sync has created nothing to remove) and every Z-Wave device is unreadable in that state anyway, so the rule entities would have been unavailable rather than useful. What is owed is a second setup path: the same one T51 needs for a Zigbee2MQTT bridge that starts late, which is watching for the upstream integration to load and building the backend then. |
| T70 | The Zooz scene numbers a hybrid leg fires on are inferred rather than observed | `profiles_db/zooz.json` now gives the four ZEN35 small buttons a `scene_id` and an `indicator_id`, both equal to the button's own number. Nothing captured says so directly. What says so is three captured facts agreeing on one numbering: the association group labels read "Button 2 - Pressed" (`z7_button_semantics`), the LED-mode parameter approved for small button 2 in the Z8 sandbox is parameter 3, and the Indicator CC ids node 36 reports are 67 to 71 labelled "Button 1 indication" to "Button 5 indication" (`z8_led_path`). The indicator half is safe to be wrong about: the worst case is the wrong LED lighting up. The scene half is not: a leg that fired on the wrong button would turn off a room somebody did not ask about. So the compiler warns (`hybrid_scene_unverified`) on every press leg whose control carries the Z7 semantics marker, which is all four of them, and the leg is behind the global option and a per-rule opt-in on top. Closing it needs what J3 needs and nothing more: node 1 in a button's Pressed group, or simply the `zwave_js_value_notification` events captured while Jayant presses each of the four buttons once. That capture answers Z7 as well. The main paddle deliberately has neither number, because nothing says which of the five it is. |
| T71 | A leg of kind (b) turns the device's own load off and only off | `_PRESS_SERVICE` maps `SELF_LOAD` to `turn_off`, because UC4's "off all, including this device's own load" is the only intent the kind exists for and the checkbox says exactly that. A user who wanted the button to toggle its own load, or to turn it on, has no way to say so. Widening it means a second field on the rule rather than a second kind, and a field nobody has asked for is a field that has to be migrated later; the narrow version is honest about what it does. |
| T72 | A hybrid leg acts on every load entity of a device, and cannot be pointed at one | `_entities_of` returns the light, switch and fan entities of the target device that are not in a config or diagnostic category. On this network every device has exactly one, so the distinction has never mattered. A device with two loads gets both, which is right for "turn this off" and is a guess for a device where the user meant one of them. The rule model has no field for an entity, only for a device and an endpoint, so fixing this properly means the rule saying which entity it means, which is a schema change. |
| T73 | A leg's firing counters do not survive a restart | `HybridLegs` keeps `hybrid_fired` and `hybrid_errors` in memory, so a restart zeroes them and the Repairs issue's error rate starts again. That is right for the rate (a fault that stopped mattering should stop being reported) and wrong for the total, which is the number somebody would want to see a week later. Persisting them means writing to the store on every firing or on a timer, and the store is the file the user's whole configuration lives in. Worth doing with a separate, cheap store rather than that one. |
| T74 | An exported profile carrying a hybrid opt-in is silently downgraded by an older Device Links | `rule_to_data` writes `hybrid` and `_rule_from_data` reads it as absent-means-none, so old files import correctly and new files import into old code with the opt-in quietly dropped. `SCHEMA_VERSION` deliberately did not move: bumping it would make every older export unreadable to fix a case that loses an opt-in rather than corrupting anything, and the version check is exact rather than a range. If the schema has to move for another reason, this is the moment to make the version a minimum rather than an equality. |
| T75 | Loop analysis reads the mirror setting and nothing else a device can do with what it receives | `forwarding_devices` asks one question: is `mirror_hub_commands` on. That is the setting the profile database models and the one the templates write, and it is not the only way a device can relay. A Zigbee device that is bound to a group which contains its own controller, or a Z-Wave device with a vendor setting nothing has curated, can close a loop this analysis cannot see. The consequence is a missed warning rather than a false one, which is the right way round for something that must stay quiet to stay read. |
| T76 | The loop warning names the devices and the rules and not the link that closes the circle | A component of three devices is reported as three devices and every rule with a link inside it. That is enough to act on (turn the mirror off on any one of them, or make one rule one way) and it is not the shortest fix: naming the single link whose removal breaks the cycle would be. Finding it means an elementary-cycle enumeration rather than a strongly connected component, which is exponential in the worst case on a graph a user can build by hand. |
| T77 | A profile diff loads every link of both sides into one payload | `profiles/diff` answers with a row per link of either side, including the ones that are the same, so the dialog can offer to show them. On this network that is a few dozen; on a fully adopted house with three protocols it is hundreds, in one message, for a screen whose first paragraph is a count. Paging it needs the command to take a cursor, which is a shape none of the other commands have yet. |
| T78 | A native on/off link can survive an on-only leg when one group carries both features | The leg takes over a **feature**, and the native link it replaces is dropped by feature name. A control whose profile entry maps two features to one association group (which `profiles_db/schema.json` permits and no shipped entry does) would keep the group for the second feature, and that group carries on and off together, so the user who asked for "only pass on" would get both natively as well as the leg. Nothing enforces the one-group-per-feature invariant the suppression relies on. Closing it means dropping the group rather than the feature, which changes what a partial refusal means for every other rule. |
| T79 | Loop analysis reads a disabled rule's mirror setting and not its links, and a disabled draft never shows a loop | Two halves of the same choice. A disabled rule contributes to `forwarding_devices` (the setting is on the device whether or not the rule is on) and contributes no edges, which is right: its links are on their way off. What follows from it is that editing a **disabled** rule in the panel never shows the loop it would close when it is switched back on, because `find_loops` filters it out along with the stored disabled rules. The user meets the warning when they enable it from the table instead, which is late but not silent. |
| T20 | A job that only queued writes to a sleeping node reports `completed` | `pending_wakeup` is in the successful set, so an apply against a battery remote alone ends green having confirmed nothing. Deliberate: a queued write to a sleeping node is the documented, expected answer (CLAUDE.md Section 10), and reporting the expected answer as `partial` teaches a user to ignore the status that means something is wrong (E4). Nothing is hidden either, because the link keeps the outcome `pending_wakeup` and the rule is not recorded as applied, so it reads as pending rather than in sync. What is missing is a status that means "done, nothing confirmed yet", and a fifth `JobStatus` member changes what every consumer switches on, so it belongs with the panel that would show it (Phase 1E) and with closing J1, which is what would tell us how often this really happens. |
| T81 | Reading one Matter node costs a round trip per endpoint | `matter._read_view` reads a Descriptor server list for every endpoint, and the coordinator reads every device of every backend at setup, so an Inovelli with 20 endpoints is 22 reads and the M1 fabric is 96. That is already the cheap version: a client list is read only where an endpoint serves a Binding cluster, which took it down from 260. The fix, if it is ever needed, is a wildcard read (`*/29/1`), which the client may well support and which nobody has tried. Worth measuring on a real fabric before optimising blind |
| T82 | A Matter Binding list's real capacity is a bound rather than a measurement | `matter_protocol.BINDING_TABLE_CAPACITY` is 8. Matter reports no capacity attribute for the Binding cluster and the specification sets no minimum, so there is no honest number to read. Exactly the shape of T43 one protocol along, and it bites in the same place: a device that holds fewer rejects a write Device Links thought would fit, and one that holds more is refused a link it could have taken. Both binding lists on this fabric are empty, so nothing is near it |
| T83 | The Matter adapter's "this control drives nothing usable" warning cannot fire for an endpoint with no Binding cluster | A consequence of T81's saving: such an endpoint never has its client list read, so `derive_emitters` cannot tell "drives nothing" from "drives something and has nowhere to keep a link" on one. The adapter says the accurate thing instead, once per read at debug: this node cannot be the source of a Matter link. A user picking a switch that turns out not to be a binding source gets a reason, and not the most specific one |
| T84 | A Matter grant is merged into an entry of the right shape rather than one known to be ours | Nothing labels an Access Control entry with who created it. `is_managed_grant` matches Operate, CASE, and a target list that is exactly the one target being asked for, which is chosen so that ownership does not need to be claimed: adding a subject to an entry of that shape grants precisely what a separate entry of ours would have. What is left is a removal, which takes our subject off an entry a third party could in principle have written first. It would still remove only the subject the rule put there |
| T85 | A Matter binding removal reports success when the grant could not be narrowed | `_revoke` logs and does not fail the link, because the binding is already gone and that is what the user asked for; what is left is a permission that permits nothing. The next removal of the same link tries again, which is why the revoke runs even when the binding had already gone. A grant nobody ever removes is one entry of somebody's Access Control list held for a link that no longer exists |
| T86 | Matter is not in the acceptance scenarios | PRD Section 15's S1 to S12 are Z-Wave and Zigbee. There is no Matter scenario to run when a write is finally approved, and the obvious one is a paddle on node 31 endpoint 2 driving the load of an Eve Energy with room in its Access Control list. Writing it is cheap; running it needs J5 |
